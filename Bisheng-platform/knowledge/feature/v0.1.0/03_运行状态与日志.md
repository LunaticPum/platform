# v0.1.0 运行状态与日志

## 原有问题与本阶段范围

重构版 API 入口此前只调用 `logging.basicConfig` 设置级别，API 与 Celery worker 没有统一的日志格式；HTTP 请求也没有在新架构中建立 trace ID 上下文，且没有基础运行状态端点。

本阶段为 API 和 worker 建立统一的控制台日志配置，为 HTTP 请求关联并回传 `X-Trace-ID`，并提供轻量健康检查。健康检查只确认 API 进程可响应，不探测数据库、Redis、MinIO 或搜索服务。

## 实际修改与实现结果

- 新增 `app/logging_config.py`，使用 Python 标准 `logging` 输出到标准输出，格式包含时间、级别、进程号、logger 名称和 trace ID；日志级别沿用 `Settings.log_level`。
- 新增 `app/log_context.py`，通过 `ContextVar` 保存请求级 trace ID；无请求上下文时日志字段为 `-`。
- 新增 `app/trace_middleware.py`。HTTP 请求携带 1 至 128 位且只包含字母、数字、点、下划线或连字符的 `X-Trace-ID` 时沿用该值，否则生成 UUID；响应统一回传 `X-Trace-ID`，请求结束后恢复上下文。
- 新增 `api/health.py` 的 `GET /health`，成功时返回 `{"status":"ok"}`。
- `app/factory.py` 装配健康路由和 trace 中间件。API 入口与 Celery worker 入口均使用统一日志配置；Uvicorn 不再覆盖该配置，Celery 不接管 root logger。
- 未增加数据库表、持久化日志、指标系统或外部依赖探测逻辑。

## 方法与设计取舍

日志采用标准库 `logging`，通过 `ContextVar` 将请求 trace ID 注入日志记录，不引入新的日志依赖。沿用原服务通过 `X-Trace-ID` 关联请求的处理思路，并将中间件放在 `app` 层、健康路由放在 `api` 层，符合新目录的职责划分。

健康检查只表示 API 进程正在响应。外部依赖就绪状态和 Celery worker 在线状态尚未纳入本阶段，避免在没有需求和业务任务的情况下引入探测、轮询或额外状态机制。

## 改进效果

API 和 worker 入口现在使用相同的日志字段，按 trace ID 可以关联单次 HTTP 请求期间产生的日志。客户端可通过响应头取得服务端采用的 trace ID；未提供或格式不合规时服务端生成新的 ID。运维或本地检查可通过 `/health` 判断 API 进程是否可响应。

当前尚无新架构的 Celery 业务任务，因此 worker 日志中的 trace ID 暂为 `-`；任务提交和执行之间的 trace ID 传递待任务迁入时实现。

## 影响与后续事项

API 新增 `/health`，所有 HTTP 响应会带 `X-Trace-ID`。不涉及库表结构或数据迁移，也未修改部署配置。

后续迁入 Celery 任务时，可按任务消息传播 trace ID，并在任务执行上下文中恢复；是否增加依赖就绪检查或 worker 状态检查，再按实际运维需求确定。
