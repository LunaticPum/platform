# 知识库微服务架构设计

本文按平台 README 设计 `knowledge-backend`。本服务只做文档库的管理、入库和检索，不做知识空间、不做 QA 库、也不生成回答。

资源事实（库是否存在、租户、版本、状态、访问方式）存在本服务。谁有什么权限存在租户与权限服务。Agent、工作流只保存资源引用和版本，通过本服务的检索接口拿片段。

## 1. 系统设计

![知识库系统设计](pics/系统设计.png)

### 1.1 领域与服务

所有接口前缀为 `/api/v1`。身份凭证和 `trace_id` 放在请求头里。写操作和 `POST /retrieve` 先过 `KnowledgeFence`：校验凭证，按凭证中的 `tenant` 读库事实，再向租户与权限 Check。

库上的 `access_mode`：

- `restricted`：所有动作都要 Check。
- `tenant_public`：同一租户的查看可直接放行；上传、编辑、管理仍要 Check。

入库动作是 `upload_file`，检索动作是 `use`。DENY 或权限服务不可用时返回错误，领域服务不执行。

#### 目录领域

目录领域负责「用户能看见、能组织的知识容器与文档元数据」。它不碰原文件字节，也不写向量。外部调用方先在这里建库、建文件夹、认文档；后续入库和检索都挂在这些目录对象上。

**`LibraryService` — 文档库容器**

- **负责**：创建一个可检索的文档库；维护库名、Embedding 模型引用、访问方式、库状态；在库下建文件夹树。库是本服务的聚合根：文件夹、文档、文件、向量索引都挂在某个库上。
- **逻辑关系**：创建库时写入 `knowledge_library`，同时生成该库对应的 Milvus collection 名和 ES index 名（物理名带租户前缀，真正建索引发生在首次入库）。建文件夹只改 `knowledge_folder`，不触发入库。
- **输入 / 输出**：入参是库名、模型引用、`access_mode`；成功返回 `LibraryView`（`id`、`name`、`access_mode`、`version`、`state`）。列表接口按租户分页返回 `Page[LibraryView]`。建文件夹返回 `FolderView`。

| 方法 | 路径 | 参数 | 响应 `data` |
| --- | --- | --- | --- |
| POST | `/libraries` | body：`name`，`embedding_model_ref`，`access_mode` | `LibraryView`：`id`，`name`，`access_mode`，`version`，`state` |
| GET | `/libraries` | query：`cursor`，`limit` | `Page[LibraryView]` |
| POST | `/libraries/{library_id}/folders` | path：`library_id`；body：`name`，`parent_id` 可空 | `FolderView`：`id`，`library_id`，`parent_id`，`name` |

**`DocumentService` — 逻辑文档与主版本**

- **负责**：把「用户眼里的一篇文档」和「某次实际上传产生的物理文件」分开。逻辑文档长期存在；每次重新上传或重建会生成新版本，但对外默认只认主版本。
- **逻辑关系**：入库成功后，由入库链路创建或更新 `knowledge_document`，并指向当前 `primary_version_id`。查询文档时读目录表，不读 MinIO 内容。
- **输入 / 输出**：按 `document_id` 查询，返回 `DocumentView`（`id`、`name`、`version`、`primary_version_id`、`file_id`），调用方据此知道当前可检索的是哪一版、对应哪个物理文件。

| 方法 | 路径 | 参数 | 响应 `data` |
| --- | --- | --- | --- |
| GET | `/documents/{document_id}` | path：`document_id` | `DocumentView`：`id`，`name`，`version`，`primary_version_id`，`file_id` |

#### 入库领域

入库领域负责「把原文件变成可检索切片」：收文件 → 排队处理 → 解析切分 → Embedding → 写索引。它依赖目录领域已有的库；不负责回答问题。

**`FileService` — 原文件入口**

- **负责**：接收 multipart 上传，把字节写入 MinIO，在 `knowledge_file` 记一条物理文件记录，初始状态为「等待」。上传前围栏检查 `upload_file`。
- **逻辑关系**：上传只落原文件和元数据，不立刻切分。调用方再显式触发 `process`，或由后续编排触发。查状态走本服务，不穿透解析引擎。
- **输入 / 输出**：入参是目标 `library_id` 和文件流；返回 `FileView`（`id`、`file_name`、`status`）。查询接口在失败时额外带 `remark`。

| 方法 | 路径 | 参数 | 响应 `data` |
| --- | --- | --- | --- |
| POST | `/libraries/{library_id}/files` | path：`library_id`；`multipart` 字段 `file` | `FileView`：`id`，`file_name`，`status`（初始为等待） |
| GET | `/files/{file_id}` | path：`file_id` | `FileView`：`id`，`file_name`，`status`，失败时带 `remark` |

**`IngestTaskService` — 解析与切分编排**

- **负责**：把已上传文件交给 Worker：更新状态为「处理中」，调用外部解析引擎，按 `split_rule`（可空，用默认规则）切成文本块。任务上下文始终带 `tenant_id`，与库租户对齐。
- **逻辑关系**：它是入库流水线的调度点。解析/切分完成后，把切片交给 `EmbeddingService` 和 `IndexService`；任一步失败则把 `knowledge_file.status` 置为失败并写 `remark`。
- **输入 / 输出**：触发接口入参是 `file_id` 和可选切分规则；立即返回变为「处理中」的 `FileView`。真正完成靠异步任务，调用方轮询 `FileService` 查最终状态。

| 方法 | 路径 | 参数 | 响应 `data` |
| --- | --- | --- | --- |
| POST | `/files/{file_id}/process` | path：`file_id`；body：`split_rule` 可选 | `FileView`，`status` 变为处理中 |

**`EmbeddingService` — 向量化（无独立路由）**

- **负责**：按库上的 `embedding_model_ref`（或本次任务临时指定的模型）把每个切片编成稠密向量。
- **逻辑关系**：只在入库任务内部被调用；不对外暴露 HTTP。输出向量交给 `IndexService` 写入 Milvus。模型不可用时抛 `KnowledgeNoEmbeddingError`，任务失败。

#### 检索领域

检索领域负责「按问题从已入库内容中拿片段」。它不改目录、不写原文件；返回带出处的文本块，由 Agent/工作流自行生成回答。

**`RetrievalService` — 混合召回**

- **负责**：在 `use` 放行后，对指定库列表做稠密召回（Milvus）+ 关键词召回（ES），合并后 Rerank，截取 `top_k`。
- **逻辑关系**：只检索主版本对应、且文件状态为成功的切片。围栏先确认每个 `library_id` 属于当前租户且状态可用。
- **输入 / 输出**：入参 `library_ids`、`query`、`top_k`；返回 `RetrievalView`，`items[]` 每项含 `document_id`、`version`、`file_id`、`page`、`text`、`score`。

| 方法 | 路径 | 参数 | 响应 `data` |
| --- | --- | --- | --- |
| POST | `/retrieve` | body：`library_ids`，`query`，`top_k` | `RetrievalView`：`items[]`，每项含 `document_id`，`version`，`file_id`，`page`，`text`，`score` |

**`CitationService` — 引用还原（无独立路由）**

- **负责**：把召回命中的切片还原成调用方可用的引用字段（文档、版本、页码、可选 bbox）。
- **逻辑关系**：挂在检索结果组装阶段；不单独建索引。意图是让下游能把答案片段对回原文件位置，而不是只返回裸文本。

**`IndexService` — 双写索引（无独立路由）**

- **负责**：入库任务在切分和向量化之后，把同一条切片同时写入该库的 Milvus collection 和 Elasticsearch index。
- **逻辑关系**：保证两条存储用同一套定位键对齐，检索时才能合并。重建索引时由入库任务再次调用；库处于重建中时对外检索返回 `KnowledgeRebuildingError`。

### 1.2 基础设施

| 组件 | 谁用 | 存什么 |
| --- | --- | --- |
| MySQL | 三个领域的服务 | 第 2 节的关系表，独立库和账号 |
| Redis | `IngestTaskService`、预览 | 本服务自己的键前缀 |
| MinIO | `FileService` | 原文件、预览文件，本服务单独 Bucket |
| Milvus | `IndexService`、`RetrievalService` | 稠密向量，见第 3 节 |
| Elasticsearch | `IndexService`、`RetrievalService` | 切片全文，见第 3 节 |
| 解析引擎 | `IngestTaskService` | 外部 HTTP |
| 租户与权限 | `KnowledgeFence` | 外部 Check；本服务不保存 Grant |

## 2. 库表设计

五张表只描述「知识资产在本服务里的事实」：哪个租户有哪些库、库里有哪些文档和文件、文件处理到哪一步。不存谁被授权——那在租户与权限服务。

![知识库库表](pics/库表设计.png)

**`knowledge_library` — 文档库**

存一个可检索知识容器的元数据。一行 = 一个库。

| 关键字段 | 含义 |
| --- | --- |
| `id` | 库主键，对外 API 与授权资源引用都用它 |
| `tenant_id` | 所属租户；围栏隔离只认这个字段，不认请求体里自带的租户号 |
| `name` | 库显示名；同一租户下不可重复 |
| `access_mode` | `restricted` 或 `tenant_public`，决定查看是否可跳过细粒度 Check |
| `state` | 库生命周期（可用 / 归档 / 重建中等），不可用时拒绝对外操作 |
| `version` | 库级乐观版本，授权 Check 可带上，避免对过期资源放行 |
| `embedding_model_ref` | 本库默认 Embedding 模型；入库向量化读它 |
| `collection_name` / `index_name` | 该库在 Milvus / ES 中的逻辑名；物理名再加 `t{tenant_id}_` 前缀 |

**`knowledge_folder` — 库内文件夹**

存库内的树状分组，方便前端浏览。一行 = 一个文件夹节点。不参与检索打分，只影响文档挂在哪。

| 关键字段 | 含义 |
| --- | --- |
| `library_id` | 所属库；文件夹不能跨库 |
| `parent_id` | 父文件夹；空表示库根下 |
| `tenant_id` | 冗余租户，查询和隔离时少一次 join |
| `name` | 文件夹名 |

**`knowledge_document` — 逻辑文档**

存用户感知的「一篇文档」。同一逻辑文档可以有多次上传历史，但对外默认只暴露主版本。

| 关键字段 | 含义 |
| --- | --- |
| `library_id` / `folder_id` | 文档落在哪个库、哪个文件夹 |
| `tenant_id` | 所属租户 |
| `name` | 文档显示名 |
| `primary_version_id` | 当前主版本；检索和对外查询都指向它 |

**`document_version` — 文档版本**

存某次入库形成的版本快照。重新上传或重建会产生新行，旧版本可保留以便追溯，但不默认参与检索。

| 关键字段 | 含义 |
| --- | --- |
| `document_id` | 所属逻辑文档 |
| `file_id` | 该版本对应的物理文件 |
| `version_no` | 版本序号；与 `document_id` 组成唯一约束 |
| `is_primary` | 是否主版本；与文档表的 `primary_version_id` 一致 |

**`knowledge_file` — 物理文件与处理状态**

存一次上传在对象存储中的实体，以及它在入库流水线中的进度。一行 = 一个 MinIO 对象 + 处理状态。

| 关键字段 | 含义 |
| --- | --- |
| `library_id` / `tenant_id` | 文件归属；上传和隔离校验用 |
| `file_name` | 原始文件名，给前端展示 |
| `object_name` | MinIO 对象键，真正读字节靠它 |
| `status` | 等待 / 处理中 / 成功 / 失败 / 重建中 / 超时；检索只认成功 |
| `remark` | 失败原因等说明，供排查 |

## 3. 向量库

设计意图：检索既要「语义相近」（用户换说法也能命中），也要「关键词精确」（专有名词、编号）。单靠一种索引都不够，所以每个文档库对应两套物理存储，入库时对同一切片双写，检索时两边召回再融合。

![向量存储](pics/向量存储.png)

**为什么按库拆 collection / index**

- 一个库一套 Milvus collection、一套 ES index，便于按库删除、重建、限流，也避免租户间数据混在同一物理集合里靠 filter 硬隔。
- 物理名带租户前缀：`t{tenant_id}_{collection_name}`、`t{tenant_id}_{index_name}`。即使逻辑名相同，不同租户也不会撞车。
- 库表里的 `collection_name` / `index_name` 是逻辑名；真正读写向量存储时拼出租户前缀。

**Milvus — 稠密语义召回**

- **存什么**：每个切片一条记录：向量 + 定位信息 + 原文片段。
- **怎么用**：把用户 `query` 编成同维向量，按相似度取候选。适合「意思对但用词不同」的问题。
- **关键字段含义**：
  - `vector`：切片的 Embedding，召回主字段。
  - `library_id` / `document_id` / `file_id` / `chunk_index`：定位到哪库、哪文档、哪文件、第几块；也是与 ES 对齐的复合键。
  - `page` / `bbox`：页码和版面框，给引用高亮用，不参与相似度计算。
  - `text`：切片原文，命中后直接带回，避免再查库拼正文。

**Elasticsearch — 稀疏关键词召回**

- **存什么**：同一批切片的全文与可过滤元数据，不做稠密向量。
- **怎么用**：对 `query` 做 BM25 等词法检索。适合型号、人名、条款号等必须字面命中的场景。
- **关键字段含义**：
  - `text`：参与全文检索的主字段。
  - `library_id` / `document_id` / `file_id` / `chunk_index`：与 Milvus 同一套键，两边结果才能去重合并。
  - `page`：出处页码。
  - `metadata`：扩展过滤条件（如文件类型、自定义标签），不进向量。

**双写与检索逻辑**

1. 入库：切分 → Embedding → `IndexService` 用同一 `chunk_index` 写入 Milvus 和 ES。
2. 检索：两边各取一批候选 → 按复合键去重 → Rerank → 截断为 `top_k` → `CitationService` 补齐引用字段。
3. 删除或重建：按 `library_id`（必要时再按 `file_id`）清两侧数据，再按主版本文件重跑入库，避免一侧有、一侧无导致召回不一致。
