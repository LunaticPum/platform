# knowledge-backend 开发约定

日期：2026-10-29

## 1. 重构目标与依据

后续开发围绕 `knowledge-backend` 的底层代码重构展开，重点是收紧服务职责、明确领域边界，并让库表、业务逻辑与基础设施之间的关系清晰。

按 DDD 的方式组织模型配置、目录、入库、检索四个领域。租户身份与权限校验作为服务边界的共同约束；知识库服务保存资源归属与状态，授权事实由租户与权限服务负责。

以当前讨论形成的设计为方向，结合实际代码、运行行为及原开源 Bisheng 的处理方式落地。`架构设计.md`、平台 README 和项目内 `docs` 都作为参考，不能作为后续开发的唯一标准。发现文档滞后或设计不适合实际场景时，应说明原因并同步修订相关设计。

当前已经明确的范围包括：

- 去掉知识空间 Space，以知识库作为知识容器。
- 服务聚焦文档管理、入库和检索，不承担 QA 库与回答生成。
- 模型配置覆盖 Embedding、Rerank、文档解析三类能力；一个库绑定一个 Embedding，入库和查询使用同一绑定，更换时重建向量索引。
- 解析与切分由 `IngestTaskService` 编排，不另外引入 `DocumentParseService`。
- 优先采用满足当前需求的简单方案，避免为了可能出现的需求提前增加层次、库表和通用机制。

这些是重构方向；现有实现的替换、数据处理和接口衔接仍需在对应阶段结合代码确定。

## 2. 按阶段推进与记录版本

重构会持续多个阶段。每个阶段应有明确的目标、改动范围和可检查的完成结果，完成后记录一个小版本，便于 review、追溯和后续继续开发。

一个小版本可以包含多个改动区域。例如，同一阶段同时完成库表重构和代码架构重构，可以归入同一个版本，但分别记录文档。

版本目录采用 `v0.1.0` 这样的形式。后续按实际完成的阶段递增；具体版本范围在开发讨论中确定，不预先把整个重构拆成固定的发布计划。

此处版本用于记录重构阶段。是否同步修改包版本、创建 Git tag 或发布服务，按该阶段实际交付需要决定，不能仅因新增 feature 文档就视为已经发布。

## 3. feature 文档在代码完成后编写

**feature 是已完成阶段的实现总结，在对应阶段的代码完成并验证后编写。**

实现之前的需求讨论、设计草案和执行计划不作为 feature，也不提前在 feature 目录下创建待实现文档或空白模板。

阶段完成时，根据实际改动创建版本目录，并按改动区域分别编写文档。目录示例如下，仅说明组织方式：

```text
Bisheng-platform/knowledge/
├── 架构设计.md
├── 261029 开发约定.md
└── feature/
    └── v0.1.0/
        ├── 库表重构.md
        └── 代码架构重构.md
```

示例中的版本和文件名不代表对应重构已经开始或完成。实际目录和文档只在阶段完成后按真实改动建立；某个区域没有改动，就不创建对应文档。

同一版本内按有独立说明价值的改动区域拆分，避免把全部变化堆进一篇文档，也不必细拆到每个文件或每个类。文档名称直接反映改动内容。

## 4. 每篇 feature 记录什么

每篇文档应让 review 的人能理解该区域为什么改、实际改了什么、结果如何。根据改动规模组织内容，至少说明：

| 内容 | 需要回答的问题 |
| --- | --- |
| 原有问题与本阶段范围 | 原实现有哪些具体问题？本阶段解决到哪里？ |
| 实际修改与实现结果 | 改了哪些库表、服务、接口或调用链？现在实现了什么行为？ |
| 方法与设计取舍 | 遵循了哪些领域边界、职责划分或其他方法？它们具体如何体现在代码中？为什么这样处理？ |
| 改进效果 | 相比原实现，职责、依赖、数据归属或运行行为有什么具体改善？ |
| 验证情况 | 做了哪些检查、测试或链路验证？结果如何？哪些受环境限制未验证？ |
| 影响与后续事项 | 有哪些接口、数据、部署或兼容性影响？还剩哪些问题？ |

按需要附上关键代码路径、迁移文件、测试入口及相关提交，方便核对；无需逐行复述代码。

方法说明要对应实际改动。例如，写“按 DDD 收紧职责”，就要说明原本混在哪里、现在由哪个领域负责、跨领域如何协作，而不是只列架构术语。

feature 只把实际完成的内容计入本阶段成果。未完成事项放在后续事项中；预期收益不能写成已经验证的效果。涉及库表调整时，应交代旧数据如何处理、是否需要迁移，以及对现有接口的影响，具体方案以该阶段实际实现为准。

## 5. 阶段完成与 review

阶段结束时，先核对代码与约定范围，完成与改动相关的验证，再编写对应 feature，交由 review。

review 中发现实现遗漏或描述不符，应修正代码或文档，使阶段记录与最终实现保持一致。跨区域的共同设计可以链接 `架构设计.md` 或同版本的其他文档，避免重复维护互相矛盾的说明。

下一阶段从已完成的代码与记录继续推进。feature 保存阶段成果，架构设计维护当前整体方向，二者随实际开发保持一致。

## 6. 分支与新旧代码并行

本次重构在基于 `jasper-261027` 创建的 `jasper-261029` 分支上推进。

重构代码放在 `src/knowledge-refactor/`，保留原 `src/knowledge/`，供运行对照、逻辑核对与代码复用。新实现逐步完善，原实现的替换及启动入口切换在对应阶段另行确定。

当前重构聚焦后端，暂不考虑前端实现。

## 7. 优先复用原 Bisheng

实现各模块前，先查阅原开源项目 `/home/skylar/platform/bisheng/` 中相应能力的设计和代码，优先复用已有的职责划分、调用方式与实现，再按知识库微服务的边界做必要裁剪和适配。

复用应结合上下文判断，不直接照搬原项目中的知识空间、平台内部依赖或其他已超出当前服务范围的能力。当前 `knowledge-backend` 的实现也用于核对已有行为与可复用逻辑，但不能因旧代码已经存在，就默认保留其混杂的职责。

**对于原设计没有对应依据的新方案，或明显偏离既有设计的调整，应先说明思路和原因，与用户讨论确认后再实现。** 避免凭空增加设计、重复实现已有能力，或自行引入额外的抽象和机制。

## 8. 目录分层与实施方式

新代码采用以下结构：

```text
src/knowledge-refactor/
├── api/
├── types/
├── domain/
├── service/
├── infrastructure/
├── app/
├── main.py
└── config.py
```

各层职责如下：

| 层或入口 | 职责 |
| --- | --- |
| `api` | HTTP 路由、参数绑定、请求依赖与响应转换，调用业务服务 |
| `types` | 请求、响应及跨层传递的数据结构，避免重复定义同一契约 |
| `domain` | 按模型配置、目录、入库、检索组织业务对象、状态和规则 |
| `service` | 编排业务操作、协调领域与基础设施调用，并明确事务边界 |
| `infrastructure` | 数据库连接与查询实现、对象存储、缓存、搜索索引、模型客户端、文档处理等技术能力 |
| `app` | 应用装配、中间件设置、资源生命周期和 Celery 等运行组件的配置；任务入口调用业务服务 |
| `main.py` | API 进程启动入口，调用应用工厂 |
| `config.py` | 环境变量、配置校验和运行参数；业务模型目录及库绑定仍从数据库读取 |

`domain` 维护业务规则，`service` 组织执行流程；`app` 负责组件装配和运行管理，`infrastructure` 提供组件的具体技术实现。按实际业务需要逐步细分模块，避免仅移动目录而继续混合职责。

**按 DDD 的分层逐层、逐个模块实现，不一次性生成整套重构代码或全部脚本。** 每一步先确定范围，再参考原实现完成相应模块和必要验证，结合 review 继续推进。

当前从 `main.py`、`config.py` 和 `infrastructure` 开始，配套实现必要的 `app` 装配。基础设施先从数据库连接与 Session 管理入手，其他组件后续逐个接入。此实施顺序用于指导当前开发；feature 仍在对应阶段代码完成并验证后总结。
