# Platform 微服务拆分约定

本文是 `/platform` 后续微服务设计和开发的简要基准。目标是让用户通过一个统一入口使用平台能力，同时让各领域服务可以独立开发、部署和扩展。

## 1. 总体结构

平台先划分为四个核心领域，并由 Frontend 提供统一用户入口：

```text
                         Frontend
                  统一登录、导航和用户入口
                    /       |       \
                   /        |        \
          租户与权限      Agent      工作流编排
                   \        |       /
                    \       |      /
                         知识库
```

四个后端领域的依赖方向如下：

```text
租户、身份、权限
        ↓
知识库 ← Agent ← 工作流编排
```

含义是：知识库提供基础知识能力；Agent 定义和运行助手；工作流可以调用已发布的助手，也可以调用知识库能力。知识库不依赖 Agent，Agent 不依赖工作流，避免循环依赖。

## 2. 领域职责

| 领域 | 主要职责 |
| --- | --- |
| 租户与权限 | 租户、用户主体、组织、角色、资源授权、身份上下文和审计 |
| 知识库 | 知识空间、文档上传、解析、切分、索引、检索、引用和知识权限 |
| Agent | 助手定义、模型与 Prompt、工具绑定、助手版本、会话和助手运行 |
| 工作流编排 | 流程构建、节点、版本、发布、运行引擎、任务和运行记录 |
| Frontend | 统一登录后的页面、导航和交互；通过各服务 API 使用后端能力 |

现有项目的初步对应关系：

- `knowledge-backend`：知识库服务
- `agent-backend`：Agent 服务（包含当前工作台相关能力）
- `agent-orch-backend`：工作流编排服务
- `frontend`：统一平台入口和各领域前端模块

该对应关系是迁移基线。服务名称可以调整，但领域职责和依赖规则必须保持一致。

## 3. 服务协作规则

1. 服务之间通过版本化 HTTP/API 或事件协作，不跨库查询，不共享业务 ORM 模型，不导入对方领域代码。
2. 工作流调用助手时保存 `assistant_id` 和明确的助手版本，只依赖 Agent 的公开运行契约。
3. Agent 或工作流使用知识时只保存知识资源引用和版本，通过知识库 API 完成目录查询、权限校验、检索和引用解析。
4. 资源所属服务负责最终权限判断。发布校验不能替代运行时校验，运行时必须再次检查资源是否仍可用。
5. 所有跨服务请求都要传递租户、最终用户、调用方和链路信息，例如 `tenant_id`、`subject_id`、`end_user`、`trace_id`。
6. 一个下游服务不可用时，不得阻断与其无关的业务；依赖该服务的功能应返回结构化错误或执行已约定的降级策略。

## 4. 隔离与部署规则

- 每个领域服务拥有独立代码、数据库 Schema、迁移、API、Worker 和发布流程。
- 可以共用 MySQL、Redis、MinIO 等基础设施集群，但必须使用独立数据库/账号、Redis 命名空间和对象存储 Bucket。
- 服务不得把对方业务数据复制成本地“影子主表”；需要关联时保存稳定资源引用和版本。
- API、Worker、定时任务和迁移使用同一服务版本发布；长任务不得依赖 API 进程内状态。
- 租户隔离和权限校验必须在后端执行，Frontend 的菜单隐藏和路由限制不能代替授权。

## 5. Frontend 统一入口

Frontend 对用户呈现为一个整体，负责统一登录、导航、页面组合和 API 调用。它可以把不同服务的页面聚合在同一平台中，但不得直接访问任何服务数据库、Redis、对象存储或内部 Worker。

各服务仍独立校验身份、租户和资源权限。Frontend 只传递用户凭证和调用上下文，不承载跨服务业务状态。

## 6. 新服务接入检查

新增或拆分服务前，至少明确：

- 所属领域和数据所有者；
- 对外 API、调用方和依赖方向；
- 租户与权限校验方式；
- 数据库、队列、Bucket 和 Worker 的隔离配置；
- 依赖故障时的错误或降级行为；
- Frontend 的路由、权限和 API 接入方式。
